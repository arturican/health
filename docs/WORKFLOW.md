# Рабочий процесс

## Выбор задачи

Источник статусов — [TASKS.md](../TASKS.md). Работа начинается с выбранного ID,
его зависимостей и карточки. Для дальних задач карточки создаются перед их выбором:
таблица — дорожная карта, а не разрешение реализовать весь продукт.

Если пользователь явно просит несколько этапов, перечисли их до изменений и
выполни последовательно. Каждый этап имеет отдельные критерии и локальный коммит.
После коммита продолжай следующий явно согласованный этап; остановка — после
всего выбранного объёма или внешнего блокера. Исторический локальный MVP описан
в [MVP.md](MVP.md); текущая матрица готовности — [REFACTORING_PLAN](../REFACTORING_PLAN.md).

## До реализации

1. Прочитай [AGENTS.md](../AGENTS.md) и карточку. В TASKS проверь строку ID и
   зависимости; в [PROGRESS.md](PROGRESS.md) найди только записи об этой задаче
   и её зависимостях (`rg -n '^## Txxx' docs/PROGRESS.md` и нужный диапазон строк).
   Старые разрешения в журнале — история, а не разрешение расширить текущий запрос.
2. Проверь `git status --short --branch`, `git diff`, `git diff --cached`
   и последние коммиты. Не перезаписывай чужие изменения.
3. Назови результат, файлы и проверки. Соблюдай бюджет из AGENTS.md.
4. При новой зависимости проверь официальный источник, engines и peerDependencies.

## Поиск и проверки без лишнего контекста

- [PROJECT_MAP.md](PROJECT_MAP.md) указывает точки входа и документы по типу работы.
  Сначала найди файлы через `rg --files`/`rg -n` в нужном каталоге, прочитай нужные
  функции, вызывающий код и тесты. Расширяй область, если зависимость/ошибка этого требует.
- Не перечитывай весь проект, README, PROGRESS и спецификации перед маленькой задачей.
  Не выводи зависимости, сборки, lock-файл, сгенерированные файлы и большие логи
  целиком без конкретной причины. Секреты не выводи и не копируй в документацию.
- До изменения выбери наблюдаемое поведение и проверку. Для кода читай
  CODING_STANDARDS и соответствующие разделы TESTING/TEST_CASES; для документации
  достаточно docs/diff check. Команды и дополнительные gates CI указаны в карте.
- Во время последовательной очереди используй связанные проверки каждой задачи;
  после последних изменений перед push обязательны полный check, build:api
  и относящиеся deploy gates. Для одной самостоятельной задачи приложения —
  полный check. CI не ослабляется.
  Повторяй проверки после новых относящихся к ним изменений или нерешённых ошибок;
  успешный прогон без таких причин повторять не нужно.
- В отчёт команды выводи итог и существенные ошибки, ограничивай длинные логи;
  не скрывай проваленные/незапущенные проверки. Не устанавливай зависимости заново,
  если lock-файл и рабочее окружение не изменились и нет ошибки установки.
- Посторонние улучшения кратко записывай в [IDEAS.md](../IDEAS.md), не реализуй.
  Карту и инструкции обновляй только при изменении фактов, на которые они ссылаются.

## Definition of Done

- Наблюдаемый результат и все критерии карточки выполнены.
- Проверки, обязательные для этой задачи, пройдены; их команды и результат записаны.
- Новая бизнес-логика и исправленные ошибки покрыты подходящими тестами.
- Нет реальных медицинских данных, секретов, обходов типов или ослабленных проверок.
- `git diff --check` и проверка локальных Markdown-ссылок проходят.
- Статус и краткая запись прогресса обновлены в том же коммите.
- В индекс добавлены только явные пути задачи; staged diff проверен перед коммитом.

`done` подготавливается перед коммитом и подтверждается его успехом. Если коммит
не создан, верни `in_progress` или `blocked` и укажи причину. Не записывай будущий
hash в документацию; фактический hash можно сообщить после коммита.

## Git

Один локальный коммит на согласованную задачу. Формат:
`type(scope): Txxx краткое действие`. Push, PR, merge и переписывание истории
требуют отдельного разрешения. Запрос `git pull` не разрешает push или PR.

После выбранного объёма остановись. Будущая задача и идея не считаются разрешёнными
лишь потому, что они присутствуют в репозитории.

## Итог задачи

Кратко укажи ID, изменения, фактические проверки и ограничения, hash/subject
коммита (либо «коммит не создан»), способ проверки через UI. Для документации
вместо UI достаточно указать, какие инструкции открыть. Для согласованной очереди
промежуточный отчёт не останавливает следующие этапы. Итог выпуска: выполненный
объём, проверки, коммиты/push, адрес/версия и конкретные оставшиеся блокеры.
