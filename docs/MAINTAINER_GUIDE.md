## Локальный запуск и перенос рабочего места

Используйте Linux или WSL 2. Версии Node и npm заданы в `.nvmrc` и
`package.json`. На новом компьютере получите доступ к репозиторию и отдельно
разрешите публичный SSH-ключ для development-секретов своим доверенным
операторским доступом. Закрытый SSH-ключ остаётся на компьютере.
[Первый запуск и выдача доступа](DEVELOPMENT.md#первый-запуск-на-новом-компьютере)

В каталоге клона в WSL или Linux выполните:

```bash
source ~/.nvm/nvm.sh
nvm use
npm run setup
npm run local:api
```

В другом терминале того же клона активируйте ту же версию Node и запустите
`npm run local:ui`. Если не меняли порты, UI доступен на `http://127.0.0.1:5173`,
а API отвечает на `http://127.0.0.1:3001/api/v1/readiness`. `setup` сверяет
зависимости по lock-файлу, получает настройки при необходимости, готовит роли,
миграции и синтетическое демо в локальном PostgreSQL. При повторном запуске
локальный том сохраняется. Подключение к рабочей базе для разработки не нужно.
[Настройка Docker, портов и локальных данных](DEVELOPMENT.md)

| Что переносите | Как |
|---|---|
| Код и документы | Сохраните работу в Git. Синхронизируйте разрешённую ветку и получите изменения на другом компьютере по инструкции ниже. |
| Доступ и общие настройки | Зарегистрируйте публичный ключ нового компьютера и запустите `setup`. В Git хранятся настройки в зашифрованном виде. |
| Порты и другие параметры компьютера | Задайте их в локальном `.env.local` по шаблону. Проверьте, какой контейнер и том указывает эта настройка. |
| Данные локального дневника | Переносите отдельно полной копией при необходимости. Записи сайта доступны через тот же аккаунт. |

[Переключение компьютеров](DEVELOPMENT.md#как-переключаться-между-компьютерами) · [Шаблон локальных параметров](../.env.local.example)

## Как продолжить задачу

1. Сверьте запрос и масштаб работы. Выполните `git status --short --branch`,
   `git diff`, `git diff --cached`, `git log -5 --oneline`. При пересечении
   с прежними правками остановитесь. Чужой staged diff тоже останавливает работу.
2. Откройте TASKS, карточку выбранного ID и запись PROGRESS по этому ID. Прочитайте
   AGENTS, WORKFLOW и ближайшие к изменению инструкции. Если карточки ещё нет,
   определите наблюдаемый результат и критерии проверки до реализации.
3. Найдите код, его вызовы и существующую проверку через карту. Для бага сначала
   воспроизведите проблему на синтетических данных и зафиксируйте регрессию.
4. Выполните проверки, обновите карточку, TASKS и PROGRESS по правилам проекта.
   Проверьте staged diff и сигнатуры секретов. Закрепите результат одним
   локальным коммитом. Отдельно запишите фактический SHA и оставшийся блокер,
   если он влияет на продолжение.

[Очередь](../TASKS.md) · [Журнал](PROGRESS.md) · [Карта проекта](PROJECT_MAP.md) · [Шаблон одной задачи](../START_ONE_TASK.md)

Чтобы передать работу следующему сеансу, достаточно такого сообщения:

```text
Продолжи Txxx по AGENTS.md.
Наблюдаемый результат: …
Последний проверенный коммит и ветка: …
Пройденные проверки и что ещё нужно проверить: …
Согласованный объём и разрешение на доставку, если оно дано: …
```

Уточнения, нужные после перезапуска чата, сохраняйте в карточке или PROGRESS.
Рабочие данные, закрытые env и копии хранятся вне Git и вне истории диалога.

## Где искать причину

| Проблема | Первые файлы и проверки |
|---|---|
| Элемент, форма, ошибка или фокус | Найдите раздел в `src/pages` и общие элементы в `src/ui`. Для формы проверьте, что происходит при ожидании, ошибке, повторе и уходе со страницы. [Правила UI](../src/pages/AGENTS.md) |
| Запись сохраняется, но список устарел | Проследите `dataAccess` → client repository → invalidation → `useDiaryQueryState`. Сверьте свежие данные, ревизию и `generation`. [Согласованность](ARCHITECTURE.md#состояние-и-согласованность) |
| Неверный ответ API, права или данные | От маршрута перейдите к соответствующему `*Records` и SQL. Сверьте схему входа и ответа, владельца из сессии, транзакцию и роль. [Правила API](../src/server/AGENTS.md) · [Контракт](API_REFERENCE.md) |
| Итог, порция, цель или график | Начните с `src/domain`, затем проверьте единицы, пропуски и даты на экране. [Расчёты](CALCULATIONS.md) |
| Вложение или восстановление | Сверьте подготовку в `src/media`, серверные лимиты и привязки, затем сценарий без записи при ошибке. [Файлы и копии](API_REFERENCE.md#файлы-и-копии) |
| Требуется новое поле или формат | Проследите поле от доменной схемы до формы, PostgreSQL, DTO, экспорта и импорта. Проверьте прежние данные, копии и совместимость миграций. [Модель данных](ARCHITECTURE.md#модель-данных) |

## Как выбрать проверку

| Изменение | Проверка, с которой начать |
|---|---|
| Markdown, ссылки и схемы | `npm run check:docs` и `git diff --check`. Новую схему отрисовать и посмотреть. |
| Чистый расчёт или схема ввода | `npm test -- путь/к/тесту.test.ts`, примеры обычного ввода, границ, ошибок и пропусков. |
| Форма, доступность или файл в браузере | `npm run test:browser:run -- путь/к/тесту.browser.test.tsx`, затем связанный E2E для сценария через API. |
| SQL, авторизация или хранение | Целевой unit/API-тест с выделенной PostgreSQL `health_test`. Проверьте доступ владельца и отказ для другого аккаунта. Для изменений собранного API также `npm run build:api`. |
| Сквозной сценарий | `npm run build`, затем `npm run test:e2e -- имя.spec.ts`. Нужен отдельный набор синтетических данных. |
| Доставка или эксплуатационные скрипты | Соответствующие Python и native gates по карте. Для frontend-архива проверьте свежий `dist` тем же валидатором, что использует CI. |

Для целевых SQL и E2E запусков задайте `TEST_DATABASE_URL` выделенной тестовой
БД по инструкции. [Настройка тестовой БД](../README.md#проверки-в-браузере-и-с-бд)

Для полного прогона применяйте `npm run local:check` после локальной настройки
и установки Chromium. Эта обёртка запускает `npm run check` с подготовленной
тестовой БД. Для изменений приложения перед разрешённым push также выполните
`npm run build:api` и связанные проверки доставки. Логи храните вне Git и
указывайте в отчёте итог и существенные ошибки.
[Окружение и команды](TESTING.md) · [Дополнительные gates](PROJECT_MAP.md#команды-и-условия)

## Выпуск и первичная диагностика

Перед публикацией зафиксируйте полный SHA, нужные проверки и область изменений.
Push в `dev` запускает штатный CI и доставку frontend. При изменении рабочего API
используйте отдельный артефакт, свежую внешнюю копию и порядок проверки SHA256 и
отката из регламента. Публикацию начинайте в пределах явного разрешения.
[Развёртывание](DEPLOYMENT.md) · [Резервное копирование](BACKUPS.md)

| Признак | Что проверить первым |
|---|---|
| `setup` останавливается | Версии Node/npm, доступ Docker, авторизацию SSH к development-секретам и текст ошибки. Существующий `.env` может требовать ручного согласования. [Настройка разработки](DEVELOPMENT.md) |
| Локальный UI открывается, дневник недоступен | Запущен ли `local:api`, верен ли порт, отвечает ли readiness и совпадает ли origin UI с конфигурацией API. [Карта запуска](PROJECT_MAP.md#команды-и-условия) |
| CI красный или `release.txt` показывает другую версию | Сверьте полный SHA ветки и CI. Найдите первую упавшую проверку. После успешной публикации сравните `release.txt` с выбранным SHA. [Устройство workflow](DEPLOYMENT.md#устройство-workflow) |
| Сайт открывается, API не отвечает | Сначала снимите статусы `/api/v1/health` и `/api/v1/readiness`. Первый проверяет процесс, второй подключение к PostgreSQL. Если API недоступен с сайта, проверьте Nginx и туннель по регламенту. [Развёртывание](DEPLOYMENT.md) |
| Не приходит письмо | Уточните, это регистрация/сброс или оповещение об отказе. У этих потоков разные точки проверки и разные подтверждённые состояния. [Почта приложения](MAIL_DNS.md) · [Независимая почта](MAIL_MONITOR.md) |
| Копия устарела или не сходится контрольная сумма | Уточните даты и результат копирования на обоих VPS. Действуйте по процедуре проверки и пробного восстановления. [Копии](BACKUPS.md) · [Независимый контроль](BACKUP_CONTROL.md) |

Окончательная приёмка связывает **SHA → CI → опубликованную версию → live API →
браузерные сценарии → сохранность данных**. Для потребительских сценариев
используйте только выделенный синтетический демо-дневник. Формы письма можно
проверить без отправки, доставку проверяют отдельно. Запишите результат, дату
и ограничения в PROGRESS и используемый регламент.
[Проверка опубликованного дневника](DEPLOYMENT.md#проверка-опубликованного-дневника)

## Как обновлять документацию

При изменении пользовательского действия сверяйте шаги и подписи в руководстве
пользователя. При изменении API, схемы или формул обновляйте соответствующий
справочник. При операционном изменении обновляйте конкретный регламент с датой,
SHA и способом проверки. Исторические срезы снабжайте ссылкой на более свежую
запись. Новое руководство добавляйте в оглавление. Схемы держите рядом с текстом,
который они поясняют, а визуальные примеры собирайте на синтетических данных.
