Frontend release 5551c0f180176938731ade285abcb7ea687983fa; последующие коммиты

## База и модель

Использован уже установленный PostgreSQL 18.3: связи, ограничения, транзакции,
RLS и согласованное резервирование записей/вложений без нового сервера СУБД.
pg и 10 SQL-миграций с checksum подходят текущему TypeScript/Zod стеку;
дополнительный ORM не понадобился. Диаграммы/карточки не стали отдельными таблицами.

18 таблиц с учётом schema_migrations:

- users, sessions — аккаунты, Argon2id и хеши сессий;
- profiles, settings — профиль, видимость, поколение/версия дневника;
- weights, products, food_entries, nutrition_days — вес, каталог, снимки порций, полнота;
- steps, workouts, energy_plans — активность и история параметров расчёта;
- files, photos, documents, lab_results — закрытые байты, материалы и ручные показатели;
- commands, legacy_metadata — идемпотентность, совместимость и marker seed.

PK/FK, владелец, уникальные даты/логины, обязательность, числовые ограничения,
индексы и правила каскадного удаления находятся в migrations. FORCE RLS на
15 личных таблицах; отдельные runtime и migration роли. Сводки вычисляются
из исходных записей по прежним формулам.

## Доступ и ограничения

Откройте сайт, войдите как health-demo с паролем из закрытого WSL файла
/home/artur/.config/health-diary/demo-credentials.json. Проверьте график веса,
выберите прошлую дату питания, откройте фото и документы. Пароль не печатается
в отчёте и не хранится в репозитории.

Сохраните recovery-secret.asc из /home/artur/.config/health-diary в защищённом
офлайн-хранилище: проверка восстановления не заменяет сохранность ключа.
Приватный экспорт имеет права 600, без парольной фразы. На VPS его нет.
Автоматических внешних уведомлений о failed backup пока нет; проверяйте timer,
журнал и свежесть offsite. RPO/RTO не гарантированы SLA; объём проверки синтетический.

База не зашифрована приложением at rest; root/администратор СУБД имеют доступ.
JSON-копии из UI не зашифрованы. Нужна сеть; публичной регистрации и интерфейса
сброса пароля нет. Лимит входа общий за proxy и хранится в памяти одного API.
Два VPS дают дополнительную точку зависимости. Общая БД/сервер не проходили reboot,
проверены рестарт собственного API и фактическое восстановление отдельной БД.

Связанные записи и файлы требуют общих транзакций, а графики — расчётов по истории.
Проверка резервирования заканчивается успешным восстановлением и проверкой доступа,
а не фактом появления файла. Эти два правила определили реализацию.

Следующая отдельная задача, которая НЕ начата: внешнее оповещение о неуспешной
или устаревшей резервной копии, с выбранным владельцем каналом доставки.
