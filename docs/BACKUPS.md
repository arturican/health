# Резервные копии PostgreSQL

Отправитель [backup_send.py](../deploy/backup_send.py) установлен на 2.26.54.81
в /usr/local/libexec. Закрытая конфигурация /etc/health-diary/backup.json
соответствует [примеру](../deploy/backup.example.json); SSH key и known_hosts
лежат рядом. Никакие пароли БД не нужны: root использует локальный Docker exec
и административное соединение внутри существующего remnawave-db.

Поток pg_dump -Fc шифруется GPG до записи на диск. Только ciphertext попадает
в /var/backups/health-diary и через отдельный ограниченный SSH key — в
/var/backups/health-diary/offsite на 159.194.208.200. Приёмник принимает только
заранее определённое имя и SHA256, не предоставляет shell/forwarding.
Секретного ключа GPG на VPS нет; публичный keyring — /var/lib/health-backup/gnupg.

Сохраняются 7 последних локальных и 14 внешних копий приложения (число копий,
не дней); исходные снимки health-cluster не удаляются. Удаление дневника не
удаляет прежние архивы немедленно. Перед передачей нового сервера другому
владельцу отдельно согласуйте судьбу архивов и recovery key.

## Управление

[Service](../deploy/health-backup.service) и [timer](../deploy/health-backup.timer)
устанавливаются на сервер БД. Расписание: ежедневно 03:30 UTC, случайная задержка
до 20 минут, пропущенный запуск выполняется после старта. Timer включён после создания health; ручные запуски и внешние SHA проверены. Команды администратора:

    systemctl enable --now health-backup.timer
    systemctl start health-backup.service
    systemctl status health-backup.service health-backup.timer
    systemctl list-timers health-backup.timer
    journalctl -u health-backup.service --since yesterday
    python3 -B /usr/local/libexec/backup_send.py --retry ИМЯ_ГОТОВОЙ_КОПИИ

Неуспех приводит к failed service; с T210 почасовой monitor сообщает по email
о первом unhealthy и восстановлении (описание и ограничения ниже).
Проверяйте журнал и свежесть копий на ОБОИХ VPS. Сбой сети не удаляет локальную
копию и не запускает retention. Лимит файла 2 GiB, резерв места 512 MiB,
общий тайм-аут 20 минут. По мере роста базы пересмотрите эти пределы.
Не публикуйте архивы и не выводите расшифрованный SQL в журнал/чат.

## Локальная проверка состояния (T206, внедрена T210)

На сервере БД оператор может использовать [backup_check.py](../deploy/backup_check.py)
рядом с backup_receive.py. Пример запуска из репозитория:

    python3 -B deploy/backup_check.py --directory /var/backups/health-diary --max-age-hours 30

30 часов — пример допуска оператора для ежедневного расписания, а не скрытый
порог: аргумент обязателен, конечен и положителен. JSON содержит healthy,
archive.status, service.status и age_seconds при доступном возрасте.
Коды: 0 — fresh + success; 1 — проблема или неизвестное состояние;
2 — неверные аргументы. Путь, имя архива, stderr systemd и содержимое не выводятся.

Возраст последнего штатного diary-архива берётся из UTC-имени снимка,
не из mtime. Ровно на границе архив свежий; время в будущем, пустой файл,
symlink или каталог вместо последнего архива дают ошибку. Cluster baseline
не учитывается. Читаются только метаданные и systemctl show фиксированного
health-backup.service (тайм-аут 10 секунд). Отсутствующий/недоступный сервис,
отсутствие запуска после старта системы, текущий запуск и ошибка не дают healthy.

Success сервиса означает завершение штатной команды, включающей передачу и
сверку SHA256; это не новая сверка второго VPS. Проверка не подтверждает
целостность/расшифровку/восстановимость, не связывает конкретный файл с запуском
и не заменяет проверку ОБОИХ VPS. Отдельный файл можно подменить вне этой модели.
В T210 проверка установлена на data VPS, расписание и email проверены.

## Email-мониторинг (T208, внедрён T210)

[backup_monitor.py](../deploy/backup_monitor.py) использует проверку T206.
Получатель выбранного пользователем канала — email через существующий Postfix
на 127.0.0.1:25. Получатель задан в закрытой конфигурации VPS,
не в репозитории. Новых SMTP-сервисов/ключей нет; хранение остаётся 7/14.

Конфигурация — JSON с ровно directory, state_directory, max_age_hours,
recipient (один ASCII bare email), smtp_port (1–65535). Порог обязателен,
конечен и положителен. Файл не symlink, принадлежит пользователю процесса,
с правами 0600, до 8 KiB. Каталог state_directory — канонический абсолютный,
с тем же владельцем и правами 0700. В нём приватные lock и state.json (0600).

    python3 -B deploy/backup_monitor.py --config /etc/health-diary/backup-monitor.json

Без --send команда выдаёт диагностический JSON, не пишет state и не отправляет
письма. --send включает отправку и сохранение состояния. Первое healthy
сохраняется молча; первое unhealthy отправляет ошибку, переход в healthy —
восстановление. Повторы того же состояния не отправляются. Адрес в state
представлен хешем; при смене адреса история начинается заново.
Свежий архив при работающем backup-сервисе — pending без письма/смены state;
устаревший архив остаётся unhealthy даже при текущем запуске.

Exit 0 — healthy/pending, 1 — unhealthy (включая успешно оповещённое),
2 — ошибка конфигурации/state/SMTP. Ошибки выводятся общим сообщением,
без адресов, stderr или содержимого. Письмо содержит только технические статусы.
SMTP socket timeout 10 секунд, общий CLI deadline 45 секунд. flock защищает
проверку/отправку/атомарную запись от параллельных запусков. При отказе SMTP
новое состояние не сохраняется; следующий запуск повторяет попытку.
Повреждённый/неприватный state отклоняется и требует проверки оператором.

Это доставка как минимум один раз: сбой после принятия SMTP DATA или перед
сохранением state может повторить письмо. Успех локального SMTP не подтверждает
доставку во входящие. Монитор на том же VPS не обнаружит полное выключение VPS;
внешний watchdog и повторная независимая сверка offsite сюда не входят.
В T210 установка выполнена, получение двух тестовых писем подтвердил пользователь.

## Комплект внедрения мониторинга (T209, внедрён T210)

Подготовлены [service](../deploy/health-backup-monitor.service),
[timer](../deploy/health-backup-monitor.timer) и
[пример JSON](../deploy/backup-monitor.example.json). Проверка раз в час,
задержка до 5 минут, Persistent. Service работает root для закрытых каталогов,
ProtectSystem=strict/ProtectHome/NoNewPrivileges, запись состояния в
StateDirectory=health-backup-monitor (0700). Адресные семейства AF_UNIX/AF_INET,
IPAddressDeny=any + IPAddressAllow=localhost; SMTP также фиксирован кодом на loopback.
Действие сетевого ограничения systemd на конкретном ядре проверяется при внедрении.

Порядок повторного внедрения после отдельного разрешения на VPS и реальные письма:

1. На data VPS сверить прежние backup-файлы и сохранить их версии. Установить
   backup_monitor.py/backup_check.py из проверенного коммита в /usr/local/libexec
   (0644), сверить неизменённый backup_receive.py рядом. backup_send.py,
   health-backup.service/timer и retention не менять.
2. Создать root-owned /var/lib/health-backup-monitor (0700). По примеру
   создать /etc/health-diary/backup-monitor.json (root:root 0600), заменить
   operator@example.test на выбранный адрес, явно проверить допуск 30 часов.
   Реальный адрес/приватный конфиг не коммитить и не выводить в чат/логи.
3. Выполнить диагностический запуск из T208 без --send: JSON должен объяснять
   состояние архива/сервиса, каталог state не должен меняться. Временные проблемы
   и ошибки конфигурации устранить до включения таймера.
4. Установить оба новых unit-файла в /etc/systemd/system (0644). Выполнить
   systemd-analyze verify для установленных файлов, затем daemon-reload.
   До enable провести разрешённую SMTP-проверку с отдельным синтетическим
   каталогом и отдельным приватным state: первое unhealthy, повтор без письма,
   затем healthy/recovery. Не портить настоящий архив и не сбрасывать его state.
5. После проверки доставки включить только health-backup-monitor.timer.
   Проверить list-timers, status и journalctl -u health-backup-monitor.service.
   Код 1/failed unit при unhealthy ожидаем даже после успешного оповещения;
   код 2 означает неисправность мониторинга/SMTP и требует проверки оператора.

Откат: disable --now только health-backup-monitor.timer, остановить monitor.service,
вернуть прежние версии его файлов/конфига при необходимости и daemon-reload.
state.json сохранить: его удаление повторно отправит первое unhealthy.
Основной backup.timer/архивы/7 локальных и 14 внешних копий не затрагивать.
После обновления проверить возраст и копии на обоих VPS вручную.

Локальные gates: systemd-analyze verify обоих новых файлов, Python deploy-тесты,
синтетический CLI smoke, docs/diff check. CI проверяет те же unit-файлы;
успех локальных gates не означает включённый timer или доставку писем на VPS.

переносимый recovery-secret.asc (0600) рядом. Он создан без парольной фразы,

отправителя; сверяйте fingerprint, не получайте ключ с произвольного keyserver.

## Восстановление

Повторяемая локальная проверка T207 — [backupRestore.test.ts](../src/server/backupRestore.test.ts).
Она создаёт синтетический дневник, настоящий custom dump, временную GPG-пару,
шифрует/расшифровывает и восстанавливает в случайную изолированную restore-БД.
Проверяются все 20 таблиц, байты файлов, миграции, RLS/ACL, чужой владелец,
отзыв сессий/ссылок и отказ повреждённого ciphertext/dump. Созданные БД/роли/ключи
очищаются; production-ключи и реальные копии не используются.
Тест входит в npm run check; зависимости окружения — [TESTING](TESTING.md).

Сначала скачайте зашифрованную копию по доверенному SSH, сравните SHA256
с сервером, проверьте расшифровку в /dev/null. Секретный ключ остаётся локально:

    gpg --homedir ~/.config/health-diary/recovery-gnupg --batch --decrypt COPY.dump.gpg > /dev/null

Восстанавливайте сначала в НОВУЮ изолированную БД, созданную администратором,
с существующими ролями из [database-roles.sql](../deploy/database-roles.sql).
Имя новой БД: health_restore_ и 32 lowercase hex из UUID без дефисов.
Создайте её с владельцем health_migrator, запретите CONNECT PUBLIC, не направляйте
на неё API. Передавайте расшифрованный поток напрямую в Docker pg_restore:

    set -o pipefail
    gpg --homedir ~/.config/health-diary/recovery-gnupg --batch --decrypt COPY.dump.gpg |
      ssh -o StrictHostKeyChecking=yes root@2.26.54.81 \
      'docker exec -i remnawave-db pg_restore -U postgres --exit-on-error --single-transaction --dbname=health_restore_REPLACE_WITH_32_HEX'

Не используйте --clean против рабочей БД. Проверьте число записей, хеши файлов,
связи, миграции и RLS; только затем планируйте отдельное переключение API.
До подключения API примените актуальные миграции, затем выполните
[revoke-restored-access.sql](../deploy/revoke-restored-access.sql) отдельным
административным соединением именно к изолированной restore-БД
(psql --set=ON_ERROR_STOP=1 --file=deploy/revoke-restored-access.sql с закрытой
строкой соединения). Скрипт принимает только health_restore_<32 hex>,
атомарно удаляет и сессии, и verify/reset-ссылки; runtime-роль его не выполняет.
При ошибке оставьте API выключенным, проверьте причину и повторите скрипт.
Проверьте нулевые количества health.sessions и health.account_tokens,
не выводя строки, хеши и адреса. Повторное выполнение безопасно.

Старый архив может вернуть удалённые записи и прежние хеши паролей.
Очистка токенов НЕ заменяет смену паролей, если снимок предшествует смене
скомпрометированного пароля: до открытия API оператор должен решить этот вопрос
для затронутых аккаунтов, включая legacy без почты. Переключение и ротация —
отдельно разрешённые операции; скрипт не меняет пароли и записи дневника.

Исходный health-cluster содержит pg_dumpall существовавшего кластера, сжатый gzip,
и предназначен только для административного аварийного восстановления.
Его нельзя автоматически применять поверх действующих БД. Он не заменяет
резервирование Docker-конфигурации и серверных настроек.

health-diary-20261016T010329Z-40a17148.dump.gpg в новую
