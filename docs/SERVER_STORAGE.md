# Переход к серверному дневнику

Решение T129 реализовано этапами T159–T178b. Серверный дневник опубликован:
PostgreSQL 18.3, 10 миграций, Fastify API, отдельные аккаунты и все восемь экранов.
Модель ниже описывает принятые решения; исходная очередь сохранена как история.
Факты эксплуатации — [DEPLOYMENT.md](DEPLOYMENT.md), итоговые проверки —
[SERVER_COMPLETION.md](SERVER_COMPLETION.md).

## Подтверждённый объём

Пользователь запросил серверное хранение вместо постоянной базы в браузере:
несколько аккаунтов с отдельными дневниками. Frontend остаётся на существующем
VPS и dev.arturican.com; новый VPS `2.26.54.81` предназначен для API и данных.
Оба VPS настроены через предоставленный root SSH; приложение работает без root.
Root нужен только администратору для первоначальной подготовки сервера.

15 октября 2026 повторное обследование подтвердило SSH root на обоих VPS,
Ubuntu 24.04.4 и существующий PostgreSQL 18.3 в remnawave-db на сервере данных.
Прежние порты 3000, 3001, 3010 и 6767 сохранены; API использует 127.0.0.1:3101.
Действующие сервисы и чужая БД не изменены.
Приватные ключи и пароли не нужны в чате.

## Схема и технические решения

Браузер обращается к `https://dev.arturican.com/api/v1/...`. Существующий Nginx
передаёт API-запросы на новый VPS по защищённому соединению с проверкой сервера.
Публичная статика остаётся на прежнем VPS. API на Node.js/TypeScript выполняет
авторизацию и проверки, PostgreSQL хранит записи и вложения на новом VPS.

- Сохраняются React, TypeScript, npm, Zod и существующие формулы. Backend
  необходим, потому что браузеру нельзя выдавать учётные данные PostgreSQL.
- Небольшой Node API с Fastify использует существующую ветку Node; проверенные
  версии закреплены в lock-файле. ORM, Redis,
  микросервисы и Kubernetes для первого серверного варианта не нужны.
- PostgreSQL даёт транзакции, ограничения связей, конкурирующие записи,
  миграции и резервное копирование. Используется pg 8.23.1 и существующий PostgreSQL 18.3;
  SQL-миграции контролируют версии/checksum и выполняются транзакционно.
- При нынешнем пределе 100 MiB вложений на дневник первоначально храним файлы
  в закрытых таблицах PostgreSQL как bytea. Запись/удаление документа вместе
  с файлом остаются одной транзакцией; резервная копия согласована с метаданными.
  При измеренном росте объёма отдельной задачей рассматривается объектное
  хранилище. Публичного каталога файлов и прямого доступа к базе из Интернета нет.
- Браузер держит данные текущего экрана только в памяти. Медицинские записи
  не сохраняются в IndexedDB, localStorage, sessionStorage или service worker
  cache после завершения перехода. Ответы API, ошибки, экспорты и файлы имеют
  Cache-Control: no-store. Статические JS/CSS можно продолжать кешировать.
- Постоянная cookie содержит только случайный идентификатор сессии. Она не
  содержит профиль, медицинские данные или пароль. При выходе очищаются данные
  в памяти и отменяются запросы, чтобы ответ старого аккаунта не попал в новый.
- При отказе API показывается ошибка и доступный повтор с сохранением текущего
  ввода в памяти. Автоматического сохранения медицинских данных в браузер нет.
  Для работы с серверным дневником требуется подключение к сети.

На frontend 127.0.0.1:53101 проброшен SSH-туннелем к API 127.0.0.1:3101.
Используются отдельный ключ, закреплённый host key и единственный PermitOpen. Нельзя пересылать медицинские данные между VPS по открытому
HTTP или отключать проверку TLS. Два сервера означают, что прежний VPS тоже
обрабатывает API-трафик; его доступ и журналы входят в границы защиты.

## Аккаунты, сессии и изоляция

- Начальный вариант: логин и пароль, аккаунты создаются доверенной
  административной командой. Открытая регистрация, SMTP и внешние OAuth-сервисы
  не нужны для первого выпуска; восстановление доступа должно быть описано
  до приглашения реальных пользователей. Email и телефон без потребности не собираем.
- Пароли хешируются Argon2id с индивидуальной солью и проверенными параметрами.
  Нужны ограничение попыток, одинаковые сообщения об ошибках входа и тесты.
  Пароли, сессионные токены и их хеши никогда не входят в экспорт дневника.
- Сессия — криптографически случайный токен; в БД только его хеш, владелец,
  срок и отзыв. Cookie __Host-health_session: Secure, HttpOnly, SameSite=Lax,
  Path=/, без Domain. При входе токен меняется; logout отзывает его на сервере.
  T163a задаёт абсолютный срок 7 суток и неактивность 24 часа; точная граница
  исключается. Активность не продлевает абсолютный срок. CSRF-токен вычисляется
  из случайного сессионного токена с отдельным префиксом; по хешу из БД его
  восстановить нельзя. HTTP-маршруты и cookie подключены в T163b.
- Изменяющие запросы требуют корректного Origin и CSRF-защиты; одного SameSite
  недостаточно. CORS для произвольных origin выключен. Доверяются только
  известные reverse proxy; клиент не определяет свой адрес через X-Forwarded-For.
- user_id API берёт только из проверенной сессии. user_id из тела/URL импорта
  не назначает владельца; запросы и связи ограничиваются текущим пользователем.
- Основной контроль выполняет API. Для личных таблиц включены
  PostgreSQL RLS с default deny и непривилегированная runtime-роль без обхода RLS.
  Контекст владельца задаётся сервером локально внутри транзакции и сбрасывается
  при commit/rollback, включая pooled connections. Миграции используют другую роль.
- Чужая запись не раскрывается ни чтением, ни ошибками, ни подсчётом, ни экспортом.
  Знание UUID не предоставляет доступ к файлу или родительской записи.

## Модель и совместимость

Каждый аккаунт имеет UUID. В пользовательских таблицах ключи и связи включают
user_id: одинаковые старые UUID в независимых импортированных дневниках допустимы.
Локальное Profile.id=self остаётся только совместимостью старого DTO/копии;
в PostgreSQL профиль определяется user_id, а не глобальным ключом self.

| Сущности | Основные правила |
|---|---|
| users / sessions | Уникальный нормализованный логин; хеш пароля; отзыв/срок сессий; timezone пользователя |
| profiles / settings | Один профиль и набор настроек на аккаунт; скрытие раздела не заменяет авторизацию |
| weights / steps / nutrition_days | Уникальность (user_id, date); ограничения значений и существующие правила обновления |
| products / food_entries | Каталог принадлежит аккаунту; состав порции остаётся снимком; FK продукта включает user_id |
| workouts / energy_plans | Текущие единицы и снимки; уникальная ревизия плана внутри аккаунта |
| files / photos / documents | Файл доступен через авторизованный API; размер соответствует bytes, MIME/контейнер проверяются сервером |
| lab_results | FK документа с user_id; дата, значение/оператор либо текст, единица и исходный референс сохраняются |

Проверка назначения файла и уникальная связь внутри каждого вида владельца
запрещают привязать один файл одновременно к фото и документу. Родительские FK
должны проверять пользователя и purpose, а не только существование UUID.
Лимиты файлов и количества записей применяются на аккаунт и проверяются внутри
транзакции с защитой от конкурентного заполнения последнего слота.

Дневные даты — PostgreSQL date и API YYYY-MM-DD, без преобразования в UTC-полночь.
Моменты создания/изменения — timestamptz в UTC. Будущее и возраст проверяются
по явной IANA timezone аккаунта, не по timezone VPS; импорт не сдвигает даты.
Числа хранятся как numeric без произвольного округления до двух знаков.
Существующие малые положительные значения должны переживать round-trip;
драйвер не превращает decimal string, null и неизвестное значение в ноль.
Целые счётчики, допустимые пределы и единицы остаются согласованными с Zod.

Изменения получают revision. API обнаруживает устаревшую правку и возвращает
конфликт вместо потери изменений другого устройства. Повторы команд защищаются
идемпотентностью внутри аккаунта; конкурентные запросы проверяются настоящей БД.
Списки имеют ограничения размера и пагинацию. Вычисляемые итоги не дублируются
как независимый источник истины. Новые сон/привычки/метрики этим переходом не добавляются.

## Переход существующего приложения

1. Добавить изолированный backend и проверки, не переключая работающий frontend.
2. Подготовить БД, авторизацию и сквозной сценарий профиль/вес для двух аккаунтов.
3. Последовательно заменить репозитории и useLiveQuery на API-чтение/команды:
   питание, активность/планы, вложения/результаты, настройки/копии. TodayPage,
   ActivitySummary и EnergySummary сейчас непосредственно используют Dexie-
   транзакции; одной замены db.ts недостаточно. Формулы переиспользуются отдельно.
4. В серверном варианте API — единственный источник записей. Тестовая конфигурация
   до переключения отделена от опубликованной версии; не создавать смесь, где
   часть одного дневника записывается локально, а часть на сервер.
5. После входа предложить импорт прежнего дневника с предпросмотром и согласием.
   Старый формат полной копии v1 читается как данные текущего владельца, включая
   файлы/результаты. Сервер повторно проверяет структуру, связи, квоты и содержимое.
   Реальные копии обрабатываются только в приложении, не через чат/AI/репозиторий.
6. Начальный импорт — в пустой серверный дневник. Непустой не перезаписывается
   автоматически; слияние требует отдельного решения. Повтор одного импорта
   идемпотентен. Ошибка не оставляет частичные записи и не портит прежний дневник.
   Существующая функция подтверждённого восстановления поддерживается отдельно:
   явный режим replace и ожидаемая changeRevision защищают от замены записей,
   изменившихся после подтверждения. Текстовая копия заменяет только текстовые
   разделы и сохраняет вложения/видимость; слияние не выполняется.
7. Проверить байты/числа/даты и вход со второго браузера. Локальная база
   не удаляется автоматически; её удаление — отдельное явное действие пользователя
   после проверки переноса. Старая база из другого origin переносится полной копией.
8. До переключения всех путей данных обновить тексты приватности и инструкции.
   Нельзя оставлять утверждение «данные не отправляются на сервер» в новом режиме.
   Старый локальный режим и его зависимости убираются после проверки миграции;
   работающая старая база без согласия не очищается.

Импорт большого JSON/файлов требует отдельных лимитов тела, памяти и времени,
ограничения параллельных задач и проверки под размер VPS. Лимит полной копии
200 MiB не становится разрешением неограниченно парсить запросы до авторизации.
История миграций БД хранит версии и checksum; повтор и одновременный запуск
контролируются. Откат приложения не подразумевает автоматический downgrade БД.

## Эксплуатация и выпуск

PostgreSQL слушает только loopback/private interface; порт 5432 публично не открыт.
API работает отдельным непривилегированным пользователем под systemd. Root и
права владельца схемы приложению не выдаются. Секреты хранятся на сервере с
ограниченными правами и в предназначенных для CI секретах, не в VITE_* или Git.
TLS, права файлов и фактическое шифрование тома проверяются при подготовке VPS;
сам выбор PostgreSQL не даёт шифрования. Условия доступа администратора к данным
нужно объяснить пользователю, а не обещать недоступность данных для root.

API logger отключён, сообщения startup/shutdown общие, без тела или реквизитов.
Nginx не журналирует API. Role-level параметры PostgreSQL исключают SQL,
параметры и обычные ошибки строк из server log; глобальные настройки чужих ролей
не меняются. Ухудшение диагностики осознанно: подробный debug выполняют только
на изолированной синтетической копии. Настройки — в DEPLOYMENT.md.
Тесты требуют TEST_DATABASE_URL отдельной health_test и создают свои случайные
БД; fallback к рабочим реквизитам запрещён.

Обновления БД/API выкатываются отдельно от существующей доставки dist в T126;
успешная статическая публикация ещё не публикует backend.

Ежедневные GPG-копии находятся на обоих VPS, приватный ключ — только локально.
Восстановление с внешнего ciphertext в изолированную БД выполнено с проверкой
хешей записей/файлов, схемы и RLS. Retention 7/14 копий, baseline отдельно;
автоматических внешних оповещений нет. Цели RPO/RTO не являются SLA и требуют
регулярной проверки по мере роста объёма. Операции и оговорки — BACKUPS.md.
Удаление аккаунта каскадно удаляет активные записи/сессии, но не старые архивы.
При disaster recovery нельзя забывать о прежних удалениях и отзыве сессий.

## Исходная очередь этапов (завершена)

Каждая строка — отдельный наблюдаемый результат с тестами и локальным коммитом.
Перед выбором следующего этапа создаётся карточка; этап дополнительно делится,
если не помещается в бюджет AGENTS.md. Точные статусы — в TASKS.md;
наличие API factory ещё не означает готовность серверного хранения.

| Очередь | Результат | Обязательная проверка |
|---|---|---|
| T130 | Изолированный API factory с liveness и безопасными ошибками, без доступа к дневнику | HTTP injection: 200/404/400/413/500, отсутствие утечек, полный check |
| Далее: запуск | Локальный запуск/production build API и обязательные настройки | Запуск/остановка, неверное окружение, отсутствие секретов в frontend |
| Далее: база | Миграции users/sessions и отдельные роли | Настоящий PostgreSQL: fresh/repeat/checksum/concurrent run |
| Далее: аккаунт | Создание аккаунта доверенной командой, хеширование пароля | Неверный ввод, повтор логина, параметры хеша, отсутствие секретов в логах |
| Далее: сессии | Вход/выход/отзыв/срок и cookie | Часы, rotation, фиксация сессии, повтор logout, отсутствие пароля в ответах |
| Далее: защита | Origin/CSRF и ограничения попыток | Чужой origin, отсутствующий токен, истечение лимита, доверенные proxy |
| Далее: профиль | Один профиль на аккаунт и timezone | RLS/две сессии, ограничения и откат |
| Далее: вес | CRUD веса с датами и revision | Уникальность по владельцу, конкурентная правка, другой аккаунт, малые числа |
| Далее: frontend | Вход и профиль/вес через API в отдельной тестовой конфигурации | Два браузера, logout/login без старого кеша, ошибки сети |
| Далее: каталоги | Отдельные API и UI-задачи каталога, затем приёмов пищи | Снимки, БЖУ, архив, чужой продукт, сохранность черновика |
| Далее: журналы | Отдельные API/UI-задачи шагов, тренировок и планов | Даты, ноль/null, ревизии, квоты и два владельца |
| Далее: вложения | Отдельные задачи файлов, фото, документов и результатов | MIME/bytes/ownership/purpose, rollback, загрузка/скачивание |
| Далее: перенос | Собственные экспорт, импорт v1 и удаление | Два аккаунта, malformed/oversize, повторы, атомарность, все 13 областей |
| Далее: резервирование | Внешняя зашифрованная копия и восстановление | Реальное восстановление только синтетической БД, отказ и оповещение |
| Далее: VPS | Проверка двух VPS, systemd, защищённый proxy и доставка API | TLS, закрытый 5432, минимальные права, logs, readiness и откат |
| Далее: переключение | Полный серверный дневник и удаление локальных путей хранения | Все сценарии API/E2E, второй браузер, no-store, отсутствие browser persistence |

Для обработчиков данных требуются unit, интеграционные тесты настоящей
PostgreSQL и browser E2E на синтетике. Проверка изоляции включает чтение,
изменение, удаление, файлы, импорт/экспорт и ошибки; тесты RLS используют
именно runtime-роль. Настройка сервера из локального терминала не заменяет
эти проверки и не переносит автоматически IndexedDB пользователей.
