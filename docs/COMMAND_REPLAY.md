# Replay и ротация служебного журнала

Решение T239 / IMP-008 / AUD-006. Это **выбранный протокол для T240/T240a**;
до их коммитов действует предел100000 и диагностика T238, автоматической
ротации нет. Сохранённые записи дневника отделены от служебных результатов команд.

## Существующие гарантии

[commands](../src/server/commands.ts) хранит hash запроса и response для ключа,
[writeCommand](../src/server/writeCommand.ts) включает HTTP route, body,
generation и optional changeRevision в descriptor. Совпавший key/hash
возвращает response без work; другая семантика того же key даёт409.
Сначала проверяется replay, затем work и квота, затем INSERT. Весь путь
проходит через [owner transaction](../src/server/userTransaction.ts):
RLS ограничивает владельца, advisory lock сериализует его записи; ошибка
откатывает изменения, revisions и вложенные команды. Records не вызывают
внешних операций; email auth не использует этот журнал.

Вложенные runCommand используются в createPlan/Photo/Document/copyMeal.
Один HTTP-запрос может занимать две строки. При clear/import work удаляет
прежний журнал и меняет generation; внешний key сохраняет результат такой
операции, позволяя повторить её после потери ответа.

Клиент [commands](../src/client/commands.ts) сохраняет неопределённые действия
только в памяти вкладки. Network/5xx повторяют исходный key/id, определённый
4xx забывает его. [session](../src/client/session.ts) при смене diary generation
меняет epoch: отменяет запросы, очищает командный кеш и перемонтирует App.
Закрытие вкладки уже сейчас теряет её неподтверждённые ключи.

## Выбранное окно и граница

Не вводим срок в часах/днях: replay доступен, пока его строка остаётся в текущем
журнале. Порог обслуживания внешней HTTP-команды —90000 уже сохранённых
строк. Прямой/вложенный runCommand сохраняет прежний абсолютный предел100000.
Запас10000 существенно превышает нынешние две строки на HTTP-команду.
Count и удаления scoped владельцем/RLS.

В execute внутри withCommand, после generation/revision guards, но **до**
изменения revisions/business work, читается persisted count под owner lock.
Признак count≥90000 фиксируется для этой попытки. Если business work валиден
и завершился, признак вызывает capacity error **до** commit/внешнего INSERT.
При существующем replay execute вообще не вызывается: старый key доступен.
Если вложенный runCommand раньше упёрся в жёсткие100000, его capacity error
тоже обрабатывается этим протоколом. Некорректный work даёт прежнюю ошибку,
не запускает обслуживание.

Первая owner transaction полностью откатывается: пользовательская команда
**не сохранена**, вложенные insert тоже. withCommand перехватывает только
capacity error и запускает вторую owner write transaction под тем же lock:

1. Проверить, что expected generation всё ещё текущая и persisted count≥90000.
2. Удалить только health.commands владельца, сменить settings.generation
   одним UPDATE. Записи, файлы, visibility, catalogSeeded и обе revisions
   остаются прежними. Коммитить оба служебных изменения атомарно.
3. После коммита вернуть409 command_rotation, фиксированное сообщение и
   X-Health-Error-Code=command_rotation. Не исполнять исходную команду повторно.

Пример границы: persisted89999 + nested + outer сохраняет90001 строку;
следующая новая валидная команда инициирует ротацию. Нельзя применять мягкий
порог отдельно после каждого nested work: rollback вернул бы89999, вторая
транзакция отказалась бы ротировать, и такой запрос застрял бы навсегда.
Обе фазы сравнивают один и тот же **persisted pre-work count**.

Если конкурентная транзакция уже сменила generation/почистила журнал,
служебная транзакция ничего не меняет и запрос получает обычный409.
Если обслуживание падает, DELETE и generation откатываются вместе;500
сохраняет ключ клиента для безопасного повтора. Работа ограничена ≤100000
строк штатного журнала, выполняется по требованию; таймер/новый сервис не нужен.

## Почему задержанный запрос не создаёт дубликат

После ротации старой строки key больше нет, а её descriptor содержит старую
generation. В execute проверка generation происходит **до business work**,
поэтому запрос получает409. Ни старый внешний key, ни вложенный id не выполнят
сохранённую ранее операцию повторно под прежним поколением. Импорт/clear replay
с сохранённой строкой по-прежнему возвращает прежний ответ без исполнения;
последующая ротация удалит и его, после чего действует generation fence.

Нельзя просто удалить строки старше TTL: запрос с прежним generation тогда
считался бы новым и мог повторно создать продукт/файл/версию плана.
Отдельный command epoch сохранил бы открытые формы, но потребовал бы нового
контракта контекстов и восстановления неопределённых операций. Для редкой
ротации раз в90000 строк используем уже проверенный generation fence.

## Вкладки, ошибки и компромисс

Получившая отказ вкладка показывает, что команда не сохранена, и перечитывает
diary-state штатной invalidation. Другие онлайн-вкладки получают новый
generation при очередном focus/online/read. Offline-вкладка до нового чтения
посылает прежний generation и получает409; автоматического переноса старого
запроса в новое поколение нет.

Смена generation перемонтирует формы: несохранённый ввод потребуется повторить.
T240a добавляет заметное сообщение для смены generation того же владельца,
включая вкладку, обнаружившую её чтением. Logout/другой аккаунт очищают notice.
Новые подтверждённые запросы с новым generation работают; прежние редакторы
не получают автоматически новую ревизию. Это намеренный UX-компромисс, не
потеря сохранённых записей. После неопределённого старого результата нужно
сначала проверить перечитанные записи; пользовательский повтор как новая
операция не является автоматическим replay старого key.

## Реализация и постоянные проверки

- **T240:** commands/writeCommand/httpErrors/app (4 файла): pre-work threshold signal,
  rollback, атомарная maintenance и409 header. Схема/SQL grants уже позволяют
  owner DELETE и UPDATE, новая migration не требуется.
- **T240a:** client/http/notices (2 файла): exact allowlist command_rotation,
  объяснение после generation/epoch remount, очистка при выходе/смене владельца.
- Итоговый push/deploy — после обеих карточек и полного check/build:api.
  Старый frontend понимает status409 и refetch, но объяснение требует нового
  bundle; поэтому выпуск включает оба. Backend не зависит от нового поля БД.

Обязательные регрессии: replay до порога;89998/89999 с nested;90000 и существующие100000 строк;
неизменные пользовательские таблицы/revisions; old-key/old-generation409
после очистки; success нового поколения; concurrent writes/maintenance ровно
одна ротация; ошибка DELETE/UPDATE откатывает оба шага; nested command rollback;
изолированность Bob; text/full export и clear/import response-loss replay;
network failure вокруг ротации; явное UI notice, закрытие/новый владелец и
сброс старых контекстов. Массовые данные только синтетические в testDatabase.

Нельзя ослаблять owner/RLS, generation/revision guards, использовать пользовательское
удаление дневника как обслуживание, автоматически повторять изменённый запрос
с новым ключом или объявлять фикс RSS/latency без измерения.
