# Тестирование

## Обязательные проверки

Дневник проверяется на уровне чистых функций, компонентов, PostgreSQL/API и
production-приложения. Legacy IndexedDB остаётся явной фикстурой изолированных
unit/browser-компонентов; рабочая сборка использует только API. При согласованной
очереди каждая задача проходит связанные проверки; после последних изменений
перед push обязателен полный `npm run check` и `build:api`.
Для самостоятельной задачи логики — полный check; для документации —
`npm run check:docs` и `git diff --check`.

| Команда | Назначение |
|---|---|
| `npm ci` | Воспроизводимая установка по lock-файлу |
| `npm run check:docs` | Локальные пути/anchors собственного Markdown и offline Mermaid syntax |
| `npm run lint` | ESLint с проверкой типов, React hooks и доступности JSX |
| `npm run typecheck` | Строгая проверка TypeScript приложения, конфигурации и тестов |
| `npm test` | Unit/компонентные тесты Vitest в jsdom, один прогон |
| `npm run test:watch` | Тот же набор в watch-режиме |
| `npm run test:coverage` | Unit/компонентные тесты с порогами покрытия V8 |
| `npm run test:browser` | Vitest UI и компоненты в настоящем Chromium |
| `npm run test:browser:run` | Тот же браузерный набор без интерфейса |
| `npm run build` | Production-сборка |
| `npm run test:e2e` | Playwright против предварительно собранного приложения |
| `npm run test:e2e:ui` | Playwright UI с выбором сценариев и timeline |
| `npm run test:design` | Визуальные эталоны и браузерные проверки дизайна |
| `npm run test:design:ui` | Тот же набор в Playwright UI с реальными кликами и снимками |
| `npm run check` | Документы → lint → типы → coverage → Browser → build → E2E |

`test:e2e` требует актуальную сборку: сначала `npm run build`. Полный `check`
делает это сам. Установка зависимостей и браузера выполняется отдельно.

Production E2E получают Content-Security-Policy из deploy/nginx.conf через
Vite preview. security-policy.spec.ts проверяет реальную блокировку inline-script
и внешнего fetch; весь набор проверяет совместимость интерфейса/файлов.
Axe внедряется через page.evaluate (браузерный драйвер), а не inline script
в DOM страницы. bypassCSP не включается; отрицательный тест подтверждает,
что inline script и внешний fetch самой страницы по-прежнему блокируются.
Vitest Browser использует отдельный dev-harness без production CSP.

## Окружение

В репозитории зафиксированы Node 24.22.0 в [.nvmrc](../.nvmrc) и npm 11.19.1
в [package.json](../package.json). `engine-strict` отклоняет неподходящую версию;
не отключай его при `EBADENGINE`. При установленном nvm:

```bash
nvm install
nvm use
npm ci
npx playwright install chromium
npm run check
```

На минимальной Linux-системе системные библиотеки браузера устанавливаются
администратором или через `npx playwright install --with-deps chromium`, если
окружение допускает это. В управляемом окружении с уже установленным Chromium:

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run check
```

По умолчанию Playwright использует свою версию Chromium. Системный браузер —
явный выбор для конкретного окружения; его совместимость подтверждается прогоном.
E2E-сервер использует `127.0.0.1:4173`, порт должен быть свободен. Старый
процесс приложения не переиспользуется. Отчёты и traces исключены из Git.

## Что тестировать

С T207 полный check также требует Docker и уже имеющийся образ postgres:18.3
(тот же образ, что в примере локальной БД и CI service). backupRestore.test.ts
использует --pull=never и host network только для выделенной loopback health_test:
pg_dump/pg_restore, временный синтетический GPG key, сравнение всех таблиц/байтов,
RLS/ACL и отзыв восстановленного доступа. Без образа тест падает, не пропускается;
настоящие ключи и архивы не нужны. Целевой запуск:
`npm test -- src/server/backupRestore.test.ts`.

После T160 полный check требует TEST_DATABASE_URL выделенной локальной
PostgreSQL health_test. Запуск контейнера описан в [README](../README.md).
SQL-тесты создают отдельную случайно именованную БД на каждый сценарий и удаляют
только её; нет fallback к рабочим реквизитам и нет skip при отсутствии БД.
CI предоставляет отдельный PostgreSQL service с вымышленными реквизитами.
`npm test -- src/server/migrations.test.ts` проверяет fresh/repeat/checksum,
ошибку SQL с rollback и конкурентные миграции на настоящем сервере PostgreSQL.

API factory в src/server проверяется существующим Vitest в Node-окружении
через директиву @vitest-environment node и Fastify inject. Команда:
`npm test -- src/server/app.test.ts`. Проверяются HTTP-статусы, заголовки,
байтовый предел, неверный JSON/MIME, безопасные 404/500; экземпляры закрываются.
Тест входит в обычный test:coverage. Это проверка HTTP-обработчиков без БД и
сетевого сокета, не production-деплой или готовая авторизация. Будущие
SQL-транзакции и ownership требуют отдельных тестов настоящей PostgreSQL.

- Чистые функции: обычный случай, границы, отсутствие значения, неверный ввод.
- Компоненты: доступные роли и подписи, ввод, действие, результат и ошибка.
- Хранилище: реальные транзакции, миграции, связи записей, повторы, rollback,
  удаление и восстановление; проверяются ошибки и неизменность прежних данных.
- Native Browser: настоящий IndexedDB, декодирование изображений, canvas,
  object URL, файлы, формы и клавиатурный фокус со стилями приложения.
- Production E2E: создание данных через интерфейс, реальные клики, загрузка и
  скачивание файлов с проверкой байтов, перезагрузка, восстановление и удаление.

Карта покрываемых областей и граничных сценариев — [TEST_CASES.md](TEST_CASES.md).
Формулы и правила отсутствующих значений — [CALCULATIONS.md](CALCULATIONS.md).

## Правила

Только синтетические данные. Тесты не зависят друг от друга или порядка запуска.
После компонентного теста очищается DOM. Время фиксируется, если влияет на
результат. Unit-тесты используют `fake-indexeddb`; Vitest Browser работает с
нативным IndexedDB и `MODE=test`, где имя базы — `health-diary-tests`. Тесты
репозиториев также создают отдельные временные базы. Данные очищаются между
сценариями; проверки всего дневника очищают все 13 таблиц, включая файлы,
показатели и metadata. Пользовательскую базу вручную не очищают.

Production E2E работают в новом контексте браузера с отдельным синтетическим
аккаунтом каждого теста. Global setup создаёт случайную PostgreSQL БД и запускает
HTTP backend с ограниченной ролью на loopback 4181; teardown удаляет только эту БД.
Создание аккаунта и сессии — fixture, CRUD выполняется через UI/API.
Один worker учитывает ограниченный слот больших копий; время фиксировано
только тестовой фабрикой, production не имеет тестового режима.
Данные создаются через UI: прямое заполнение IndexedDB, подмена
репозиториев и бизнес-ответов не заменяют пользовательский сценарий. Синтетические
изображения и PDF создаются тестами. Внешние сервисы не вызываются; E2E учитывают
ошибки страницы/консоли и HTTP-запросы за пределы локального приложения.

Используй `getByRole`, `getByLabelText`, `findByRole` и ожидаемые пользователем
результаты. Не проверяй внутренний state, имена CSS-классов или большие snapshots.
Ожидай состояние через assertions, не через произвольные задержки. Для фокуса
после React-эффекта используй `waitFor(() => expect(element).toHaveFocus())` в
RTL либо ожидающее browser/Playwright assertion. Наличие нового DOM ещё не
означает завершение эффекта. Для асинхронного checkbox полноты дня используй
клик, затем ожидай `toBeChecked()`; мгновенная проверка состояния внутри
`check()` может опередить запись в IndexedDB.

Ошибки хранилища воспроизводятся контролируемыми fault hooks/моками на подходящем
уровне с проверкой rollback, сохранения формы и повтора. Если такой тест вызывает
ожидаемое сообщение консоли, проверяй именно синтетическую ошибку; не отключай
проверку консоли целиком и не скрывай неожиданные ошибки.

Регрессия начинается с воспроизводящего теста. Не используй `.only`,
`passWithNoTests` и необъяснённый `.skip`. Покрытие само по себе не доказывает
качество. `npm run test:coverage` проверяет весь src,
кроме тестов и точки запуска main.tsx (её проверяет E2E). Пороги: 80% строк,
инструкций и функций, 70% ветвей. Новые файлы
включаются даже без импорта тестами. HTML-отчёт — coverage/index.html.
Это покрытие unit-набора; результаты Browser и E2E в него не объединяются.
Не ослабляй проверки ради зелёного результата. Если тест нельзя выполнить, укажи
причину и фактически пройденные команды.

Небольшие изменения текста или оформления могут проверяться вручную без нового
автотеста. Правки логики, хранения, импорта и вычислений требуют подходящих тестов.

## Ручная проверка

Axe проверяет компоненты и все восемь production-экранов в настоящем браузере
со стилями, включая применимые
правила контраста и доступных имён. Отдельный отрицательный тест подтверждает,
что кнопка без имени обнаруживается. Axe не заменяет проверку клавиатуры,
содержательности подписей и screen reader.

Перед завершением UI-задачи проверь узкий экран, клавиатуру, читаемость, пустое
состояние и отсутствие ошибок в консоли. Production-набор запускается в Desktop
Chrome и Pixel 7 с настоящим mobile/touch-контекстом шириной 375 px. Это проверка
Chromium: совместимость Firefox/Safari и работа screen reader не подтверждены.
Дополнительный [responsive E2E](../tests/e2e/responsive.spec.ts) открывает все
восемь разделов на 320, 375, 768, 1024 и 1440 px с длинными синтетическими
значениями и документом. Проверяются границы страницы и элементов управления.
Отдельный сценарий 1024×400 проверяет прокрутку бокового меню и открытие настроек
с клавиатуры; горизонтальное скрытие переполнения не используется как исправление.
[График веса](../tests/e2e/weight-chart.spec.ts) проверяется кликом и настоящим tap
в mobile-контексте: выбор дат, клавиатура/фокус, правка и удаление выбранной записи,
адаптивность и axe. Unit-тесты отдельно проверяют пустую/одиночную/постоянную
историю, точность значений и обновление выбора.
Ручной smoke не заменяет обязательные автоматические проверки. Перед fullPage
снимком верни прокрутку к началу; используй только синтетические данные.

## Тесты прямо в браузере

### Проверки дизайна

После `npm run build` запусти `npm run test:design` или `npm run test:design:ui`.
В Playwright UI выбери оба проекта в фильтре Projects для Desktop и mobile;
по умолчанию интерфейс может показывать только Chromium. Headless-команда
выполняет оба проекта автоматически.
Набор входит и в обычный `test:e2e`, поэтому полный `check` и CI запускают его
автоматически. [Браузерные контракты](../tests/e2e/design-contract.spec.ts)
проверяют основные цели касания ≥44×44 CSS px и геометрию пиктограмм на
320/768/1440 px, видимую обводку при настоящих Tab-переходах и отключение
движения при `prefers-reduced-motion: reduce`.

[Визуальные регрессии](../tests/e2e/design-visual.spec.ts) сравнивают 28 небольших
PNG-эталонов: девять пиктограмм и пять состояний области графика для каждого
Desktop/mobile-проекта. График проверяется с одной точкой, несколькими измерениями
на неравномерных датах и выбором первого/последнего измерения на 320/375 px.
Дополнительно на 320/768/1440 px проверяются круглые различимые маркеры и линия,
толщина которой не масштабируется вместе с SVG. Профиль и веса создаются формами;
время фиксировано, ошибки консоли и внешние HTTP-запросы запрещены.

Эталоны охватывают SVG-графику без текста, а не полноэкранную типографику:
системные шрифты различаются между ОС. Снимки имеют CSS-масштаб, анимация и каретка
отключены. Допуск числа различающихся пикселей — ноль; стандартный цветовой
порог Playwright учитывает небольшие различия растеризации. Эталоны не привязаны
к имени ОС, Desktop/mobile имеют отдельные файлы. При обновлении Chromium
обязательно просматривай diff: несовпадение не означает, что эталон надо заменить.

Текст выше графика может располагать его на дробной координате страницы. Перед
снимком тест временно сдвигает контейнер через relative top/left не больше чем
на половину CSS-пикселя до целочисленного начала координат и восстанавливает
inline-стили в finally. Размер, данные и оформление графика сохраняются;
трансформация не используется, чтобы не сдвигать уже растеризованный слой.
Один и тот же эталон проверяется с системным шрифтом, Arial и DejaVu Sans
(с системным fallback), поэтому шрифт текста за пределами снимка не должен
влиять на сравнение. Это нормализация только тестового снимка, не CSS приложения.

`npx playwright show-report` открывает HTML-отчёт. При несовпадении доступны
expected/actual/diff, screenshot страницы и trace; CI сохраняет отчёт и артефакты
ошибки на семь дней. Для намеренного изменения дизайна сначала просмотри новый
результат и diff, затем обнови только нужные эталоны:

```bash
npx playwright test design-visual.spec.ts --update-snapshots
npm run test:design
```

PNG в `tests/e2e/design-visual.spec.ts-snapshots/` хранятся в Git и проверяются
вместе с изменением дизайна. Автоматическое обновление при обычном запуске/CI
не используется. Эти проверки дополняют axe и адаптивные сценарии; они не
подтверждают внешний вид всего приложения в Safari/Firefox.

### Vitest и Playwright UI

`npm run test:browser` открывает Vitest UI с тестами компонентов в Chromium.
Открой адрес runner из терминала (по умолчанию
`http://localhost:51204/__vitest__/`): можно выбирать файлы и отдельные тесты,
перезапускать сценарии и просматривать Report/Console. Выбор файла, теста и
просмотр результата проверены настоящими кликами в Chromium; фактический прогон
записан в [PROGRESS.md](PROGRESS.md).
`npm run test:browser:run` — тот же набор в headless-режиме для quality gates.
`npm run build`, затем `npm run test:e2e:ui` — Playwright UI: запуск сценариев,
просмотр реальных кликов и timeline. Эти инструменты доступны только разработчику
и не входят в production-приложение. На WSL при отсутствии дисплея используй
headless-команду; интерфейс runner открывается по напечатанному локальному адресу.

## CI

### Проверка опубликованного редизайна

Локальные API E2E используют изолированные аккаунты и фиксированное время.
Их нельзя запускать против опубликованного аккаунта. Отдельная конфигурация
tests/deployed/playwright.config.ts проверяет HTTPS, release.txt, редирект и 404;
для запуска задайте EXPECTED_RELEASE полного SHA и передайте конфигурацию Playwright.
Она не запускает тестовую БД/локальный сервер и не использует личный профиль
браузера. Полный smoke опубликованного API и проверка перезапуска фиксируются
отдельно при развёртывании; локальный check не выдаётся за VPS-проверку.

### Автоматические проверки перед доставкой

Workflow [.github/workflows/check.yml](../.github/workflows/check.yml) проверяет
push и pull request в dev/master; доступен ручной запуск. Ubuntu 24.04 использует
Node из .nvmrc и npm ci с npm cache. Независимые jobs выполняют все фазы локального
npm run check: static — docs/lint/typecheck, coverage — unit/API с PostgreSQL,
browser — Native Browser, build — production-сборка и deploy-проверки.
Chromium с системными библиотеками устанавливается только в browser/E2E jobs.

Build один раз сохраняет dist. Два E2E jobs скачивают этот артефакт по его
неизменяемому ID и запускают соответственно chromium и mobile-chromium.
Каждый job имеет отдельные PostgreSQL/API, часы и слот резервного копирования;
workers: 1 сохраняется. fail-fast: false позволяет получить результат обоих
проектов. Локально те же выборки можно проверить после npm run build командами
`npm run test:e2e -- --project=chromium` и
`npm run test:e2e -- --project=mobile-chromium`; запускайте их последовательно,
так как локальная конфигурация использует фиксированные порты API/preview.

Итоговый job check требует success всех обязательных jobs; ошибка, отмена
или пропуск любого gate блокируют успех и deploy. Actions закреплены по SHA;
права contents: read, checkout credential persistence отключён. Артефакт сборки
и отчёты проваленных браузерных/E2E-проверок сохраняются на 7 дней; имена отчётов
разделены по проекту и попытке. Только синтетические данные, без личных фото,
медицинских документов и секретов. Успех локальных команд не подтверждает
удалённый workflow: его состояние проверяется отдельно после push.

Build также запускает `python3 -B -m unittest discover -s deploy -p 'test_*.py' -v`,
`systemd-analyze verify` для backup monitor service/timer и
`python3 -B deploy/verify_build.py dist`. После успешного итогового check push
или ручной workflow в dev публикует тот же dist по ID артефакта через deploy job;
PR и master не публикуются. Настройки окружения, проверка версии и откат описаны
в [DEPLOYMENT.md](DEPLOYMENT.md). Локальный npm run check остаётся последовательным.

## Проверка документации

npm run check:docs запускает synthetic node:test cases и локальный обход
всего собственного Markdown, включая design. Проверяются пути и fragments
Markdown: заголовки, кириллица/URL encoding, суффиксы повторов и HTML anchors.
Fenced примеры исключены; зависимости, Git и generated outputs не обходятся.
Реализовано используемое проектом подмножество ссылок/заголовков, включая явные
reference links; это не полный CommonMark parser и не проверка внешних URL.
Правила anchors сверены с
[GitHub section links](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#section-links).
Mermaid проверяется отдельным этапом того же check:docs: mermaid12.2.0 и
существующий jsdom, без внешней сети. Есть valid/invalid flowchart/ER/sequence,
fences/empty/unclosed fixtures. Parse не заменяет визуальную проверку схем.
См. [MERMAID_TOOLING](MERMAID_TOOLING.md).
