# T262c — Выбран существующий внешний SMTP

21.10.2026 пользователь выбрал «Использовать уже имеющийся внешний SMTP»
после отказа в PTR (T262b). Результат этой задачи — зафиксированный выбор,
проверенные ограничения текущего стека и состав необходимых параметров.
Это решение, не переключение транспорта и не успешная доставка.

Исходный devda764f0 clean. Только docs: MAIL_MONITOR/BACKUP_CONTROL/AUDIT/
IMPROVEMENTS, TASKS/PROGRESS, карточка T262 и эта карточка. Проверки: read-only Postfix/SASL preflight,
использование From в Python, review, check:docs/diff/staged/secret scan.
Не менять конфигурацию MTA/data VPS, публичные DNS, sender или state;
не создавать сторонние аккаунты и не запрашивать пароль/ключ в чате.

## Известно и проверено

Frontend Postfix поддерживает Cyrus SASL. libsasl2-2, libsasl2-modules,
libsasl2-modules-db уже установлены в версии2.1.28+dfsg1-5ubuntu3.1.
TLS verify включён, wrappermode=no, smtp_sasl_auth_enable=no,
defer_transports=smtp. Нового пакета или общего upgrade не требуется
для этого предварительного выбора; provider-specific требования ещё неизвестны.

backup_monitor.py, watchdog_monitor.py, offsite_monitor.py используют
no-reply@auth.arturican.com в заголовке From; smtplib send_message берёт
из него также envelope sender. Конфиг этих CLI принимает ровно пять прежних
полей и не содержит sender. Нельзя считать SMTP login автоматически разрешением
отправлять от произвольного домена. Если этот From разрешён сервисом, Python
и units могут остаться прежними; иначе нужна отдельная небольшая задача
sender/rewrite с проверкой итогового envelope/header/DKIM и без изменения data mail.
Переписывание подписанного From через smtp_generic_maps может сломать DKIM;
повторная подпись провайдером не предполагается без подтверждения.

Запрошены публичные параметры: название сервиса/SMTP-host, port, STARTTLS или
TLS-on-connect, допустимый From. Они пока не получены; провайдер не угадывается
по адресу получателя, аккаунт/доступ не выбираются за пользователя.
После ответа сверить официальные инструкции сервиса и native EHLO/TLS;
реальный AUTH — только после закрытого ввода credentials.

## Следующая реализация после параметров

Разбить конкретные изменения в карточках≤5 implementation files/≤250 lines:
1. Relay-only config и отдельный gate: фиксированные host/port/TLS/CA/name,
   SASL AUTH после TLS, отсутствие direct-MX fallback/другого маршрута.
   Synthetic auth-log regression с non-email username: прежнего @-filter
   недостаточно для новых SASL diagnostics; защитить journal и rsyslog до AUTH.
   Не включать debug_peer_list/SMTP AUTH tracing и не проверять неверный пароль
   на реальном сервисе (опасность блокировки аккаунта).
   Сохранить существующие standalone data/monitor gates неизменными.
2. Если требуется другой From — отдельно sender policy, совместимость data,
   проверка полученного заголовка/envelope/domain authentication.
3. Native installation с before/rollback, root0600 credentials/maps, queue empty,
   synthetic fixture без внешней отправки; сохранить privacy/loopback/tempfail.
4. Synthetic письмо прежнему recipient, receipt, затем T253a/T254c alert/recovery
   и timers. Локальный DATA250 и queue drain не доказывают inbox delivery.

Credentials вводит оператор в своём терминале с отключённым echo. Будущая
проверенная процедура передаст их по существующему SSH через stdin в root0600
файл MTA; plaintext и compiled map root0600, exact [host]:port lookup key.
Не применять static:user:password. Не argv/env/Git/chat/AI или monitor JSON. На этом шаге процедура
не реализована, файл с паролем не создан, AUTH/почта не отправлялись.

Существующие state сохраняются: ключ дедупликации не учитывает relay/From/port.
Поэтому новую доставку проверять отдельным synthetic state; начальный healthy
письма не создаёт, watchdog требует два наблюдения. Ошибка внешнего SMTP после
локального принятия Python не видна — receipt обязателен. Независимость требует,
чтобы ни транспорт, ни его credentials path не зависели от data VPS.

Parent T262 остаётся blocked до параметров/доступа/проверки. Отказ в PTR
закрыл прежний direct-to-MX путь, но не является проверкой нового relay.
