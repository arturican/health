# T241a — Ограниченное хранение событий API

Зависимость: T241. IMP-010 / AUD-009. Статус — в TASKS.md.
Результат: health-api stdout/stderr направлены в journal namespace health-diary;
его собственный drop-in задаёт persistent16MiB/runtime8MiB, rotation1h,
retention7day и запрет forwarding. Дополнительный unit rate120/60s; жёсткий
rate30/type/min остаётся в приложении. История при лимите объёма может быть
короче7day; activefiles учитываются с особенностямиjournald, не обещать
точное удаление каждого сообщения в секунду. Глобальная journald policy не меняется.

Файлы реализации: health-api.service, health-api-journal.conf,
verify_api_units.py (3/250). Python test отдельно.
Проверка CI: policy/INI invariants и штатный systemd parser для unit;
ExecStart предварительно сверяется с .nvmrc/контрактом, в временной копии
подменяется на /usr/bin/true, поскольку production Node path отсутствует в CI.
Не считать это запуском API/проверкой journalddaemon. Нативный exact unit verify,
namespace activation, synthetic event и health/ready — release gates на VPS T260.
Локально255, sudo недоступен; реальное время retention не проверяется ожиданием7дней.
Критерии: validator отвергает отсутствие namespace/forwarding/unbounded limits,
CI вызывает его; docs описывают установку/чтение/доступ/откат и пределы проверки.
Все Python deploy tests, validator, docs/diff/staged review.

CI уже запускает unittest discover deploy/test_*.py: новый positive test
проверяет настоящий unit через validator/nativeparser, negative tests —
искажённые policy/namespace. Отдельный повторяющий workflow step не добавлен.

Review выявил обход ConfigParser DEFAULT и непроверенный unit rate.
Негативные cases сначала FAIL, затем validator запретил DEFAULT inheritance,
проверяет namespace/identifier/stdoutstderr, interval60s/burst≤120 и bounded
journalpolicy. Все48 deploy tests PASS; runtime activation всё ещё gate T260.
