# Health Diary — правила для Codex

Личный дневник здоровья: React + TypeScript + Vite, Fastify API и PostgreSQL.
Рабочие экраны используют сервер; Dexie/IndexedDB сохранены для legacy и тестов.
UI по-русски, идентификаторы по-английски. Совместного доступа и AI нет.

## Одна задача → проверки → локальный коммит

1. Проверь `git status --short --branch`, `git diff`, `git diff --cached`,
   `git log -5 --oneline`. Не трогай прежние незакоммиченные изменения;
   при пересечении или чужом staged diff остановись и опиши конфликт.
2. Прочитай [WORKFLOW.md](docs/WORKFLOW.md), выбранную карточку `docs/tasks/Txxx.md`,
   её статус/зависимости в [TASKS.md](TASKS.md) и относящиеся записи
   [PROGRESS.md](docs/PROGRESS.md). Используй поиск по ID, не читай журнал целиком.
3. Найди файлы через [PROJECT_MAP.md](docs/PROJECT_MAP.md) и `rg`;
   сначала изучи нужный модуль, его вызовы и тесты, расширяй поиск при необходимости.
   Дополнительные документы читай по типу задачи, как указано в карте.
4. До изменений назови ID, результат, файлы и проверки. Это не запрос подтверждения.
   Если карточки нет, создай её в рамках согласованной задачи до реализации.
5. Выполни только согласованный объём, достаточные проверки и `git diff --check`.
   Обнови TASKS/PROGRESS тем же коммитом; проверь staged diff и отсутствие секретов.
6. Создай один локальный коммит и остановись. Краткий отчёт — по WORKFLOW.

- «Следующая»/«начать проект» разрешает ровно одну ближайшую незавершённую задачу
  с выполненными зависимостями. Явные несколько этапов выполняются последовательно,
  каждый со своими критериями, проверками и коммитом. «Написать приложение полностью»
  разрешает очередь локального MVP, но не IDEAS.
- Бюджет: один наблюдаемый результат, до 5 вручную изменяемых файлов приложения
  и до 250 добавленных/удалённых строк реализации. Небольшие тесты/документация,
  lock-файл и неизменённый шаблон генератора считаются отдельно.
  При превышении до реализации предложи подзадачи; исключение — только явно разрешённое.
  Не ужимай код и не удаляй тесты ради бюджета.
- [IDEAS.md](IDEAS.md) не разрешает реализацию. Посторонние улучшения записывай туда.
  Новые зависимости, рефакторинг вне задачи, серверные расширения, AI, синхронизация
  и интеграции требуют отдельной задачи. Никаких фоновых циклов/автопрохода backlog
  и параллельных агентов для других задач; review текущей задачи можно делегировать.
- Обновляй карту и инструкции только при изменении описанных фактов.
  Документация не заменяет проверку актуального кода.

## Git и окружение

- Разрешён один локальный коммит на завершённую согласованную задачу.
  Без отдельного разрешения запрещены push, PR, merge, rebase, amend, удаление веток,
  перезапись истории и деплой. Не меняй глобальный Git, автора, модель,
  права/безопасность Codex и подключения инструментов.
- Не выполняй auto-stash, reset, clean, checkout/restore поверх чужих изменений.
  Добавляй только явные пути; запрещены `git add .`, `git add -A`, `git commit -a`.
  Сообщение: `type(scope): Txxx краткое действие`;
  типы: feat, fix, test, refactor, docs, chore. Hash сообщай после коммита.
- При блокере сначала попробуй безопасно исправить окружение в разрешённых каталогах.
  Не коммить задачу завершённой с проваленными обязательными проверками.
  При неудачном коммите верни статус из done; неустранённый блокер — blocked.

## Команды и качество

- WSL/Linux: `nvm use`; Node — [.nvmrc](.nvmrc), npm — [package.json](package.json).
  `npm ci` нужен при установке/изменении зависимостей, не перед каждой задачей.
  Новые версии проверяй по официальным источникам, фиксируй совместимость и версии.
- UI: `npm run dev`; API: `npm run dev:api` (настройка БД — в README).
  Сборка: `npm run build`, `npm run build:api`.
- Только документация: `npm run check:docs` и `git diff --check`.
  Изменения приложения: обязательный `npm run check`; сборка не заменяет типы/тесты.
  Требования окружения, целевые проверки и дополнительные gates CI —
  [TESTING.md](docs/TESTING.md) и карта. Повторяй после новых изменений/при ошибках,
  не запускай снова успешные проверки без причины. Длинные логи ограничивай,
  показывай существенный результат и ошибки. Не ослабляй проверки ради успеха.
- Для кода читай [CODING_STANDARDS.md](docs/CODING_STANDARDS.md): strict,
  без any/@ts-ignore/as unknown as; внешний ввод unknown + runtime-валидация;
  расчёты вне JSX, без дублирования производных сумм в state и абстракций на будущее.
- Бизнес-логика: обычный случай, границы, неверный ввод, отсутствие данных.
  Баг — regression-тест. Компоненты — роли, подписи, действия; не внутренний state/CSS.
  Изоляция, очистка DOM/хранилищ, явная дата, без внешних сетевых запросов,
  задержек ожидания UI, .only, необъяснённых .skip и passWithNoTests.
  Текст/стили допускают ручную проверку; не добавляй тесты, повторяющие реализацию.

## Непереговорные ограничения

- Только синтетические данные в разработке, тестах, скриншотах, логах, Git и AI.
  Не загружай реальные анализы/фото людей в Codex; не выводи секреты.
- Фото — сравнение по датам, без диагнозов, степени ожирения и процента жира.
  ИМТ — справочная категория с ограничениями, не диагноз и не оценка человека.
- Цель калорий и расход различаются; не учитывай дважды активность и те же шаги/тренировки.
  Нет данных ≠ ноль; дефицит не «хорошо», избыток не «плохо».
  До изменения расчётов читай [CALCULATIONS.md](docs/CALCULATIONS.md);
  формулы/пороги уточняй в задаче, не придумывай медицинские пороги.
- Локальная БД не гарантирует шифрование/сохранность. Без внешней аналитики,
  удалённых шрифтов, отправки документов, frontend-ключей и публичных ссылок на вложения.
  Для данных/авторизации/файлов читай [PRIVACY_SECURITY.md](docs/PRIVACY_SECURITY.md).
  Совместный доступ нельзя имитировать клиентской проверкой роли.
